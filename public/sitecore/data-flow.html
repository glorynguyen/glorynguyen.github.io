Sitecore Content SDK — Route Data Flow

What happens when you navigate to localhost:3000/{site}/{locale}/vincent

1
Browser Request
Browser → Next.js Server
The browser issues a GET request. Next.js App Router matches the URL to the file-system route structure. There is no middleware.ts in this project — routing is handled entirely by the dynamic segment structure.
// URL segments map to these dynamic segments: localhost:3000/mysite/en/vincent ↓ ↓ ↓ [site] [locale] [[...path]]
// Matched file: src/app/[site]/[locale]/[[...path]]/page.tsx
Next.js App Router Server
2
Nested Layouts Execute (outside-in)
app/layout.tsx → app/[site]/layout.tsx → app/[site]/[locale]/[[...path]]/layout.tsx
Next.js runs layouts from outermost to innermost before the page. Each layout wraps the children from the next level.
// 1. app/layout.tsx — root HTML shell return <html><body>{children}</body></html> // 2. app/[site]/layout.tsx — Bootstrap (client analytics) const { isEnabled } = await draftMode() return <> <Bootstrap siteName={site} isPreviewMode={isEnabled} /> {children} </> // 3. app/[site]/[locale]/[[...path]]/layout.tsx — cache params setCachedPageParams({ locale, site }) // used by notFound() pages return <>{children}</>
Server Components Bootstrap = Client
3
Page Component — Draft Mode Check
src/app/[site]/[locale]/[[...path]]/page.tsx
The async page component receives params. It checks Next.js Draft Mode to decide which SitecoreClient method to call.
const { site, locale, path } = await params setRequestLocale(`${site}_${locale}`) // for next-intl const draft = await draftMode()
Decision — Is Draft Mode enabled?
Normal draft.isEnabled = false — normal production render.
Calls client.getPage(["vincent"], { site, locale })
Preview draft.isEnabled = true — editing or Design Studio.
Reads preview cookies via client.getPreviewData(headers), then calls client.getPreview() or client.getDesignLibraryData()
Server Next.js Draft Mode
4
SitecoreClient.getPage()
src/lib/sitecore-client.ts → @sitecore-content-sdk/nextjs/client
SitecoreClient is a singleton initialised once with sitecore.config.ts. getPage() uses the internal LayoutService to issue a GraphQL query to the Sitecore Edge API.
// src/lib/sitecore-client.ts const client = new SitecoreClient({ ...scConfig // api.edge.contextId, defaultSite, defaultLanguage, etc. }) // Called from page.tsx (normal mode): const page = await client.getPage( ["vincent"], // path segments { site, locale } // PageOptions )
// Internally, LayoutService issues a GraphQL query to: https://edge-platform.sitecorecloud.io/v1/content/api/graphql/v1 ?sitecoreContextId={SITECORE_EDGE_CONTEXT_ID} // The query retrieves: // - Route layout definition (placeholders + renderings hierarchy) // - Component fields (Text, Image, Link, RichText, ...) // - Context data (language, site, pageState)
Server GraphQL / Sitecore Edge
5
Page Found or 404
page.tsx — post-fetch guard
If the Sitecore content tree has no item at /vincent for the requested site + locale, getPage() returns null and Next.js renders the not-found page.
Decision — Did Sitecore return a page?
null No content item found at /vincent — calls notFound() → renders app/not-found.tsx
Page Returns a Page object containing layout + mode — rendering continues
Page object shape
{ layout: { sitecore: { context: { site, language, ... }, route: { // root rendering node name: "vincent", placeholders: { "headless-header": [ ...renderings ], "headless-main": [ ...renderings ], "headless-footer": [ ...renderings ] } } } }, mode: { isNormal: true, isEditing: false, isPreview: false, isDesignLibrary: false } }
6
Providers — Client Context Setup
src/Providers.tsx + src/app/[site]/[locale]/[[...path]]/page.tsx
The page wraps the layout in two providers before rendering. Both are Client Components that hydrate on the browser side.
// page.tsx return value: <NextIntlClientProvider> // i18n dictionary for client components <Providers page={page}> // SitecoreProvider (client map, import map) <Layout page={page} /> </Providers> </NextIntlClientProvider> // Providers.tsx (client component): <SitecoreProvider api={scConfig.api} componentMap={components} // .sitecore/component-map.client.ts page={page} loadImportMap={() => import('.sitecore/import-map.client')} > {children} </SitecoreProvider>
Client Components Server renders shell
7
Layout — AppPlaceholder renders components
src/Layout.tsx
Layout is a Server Component. It extracts route and mode from the Page object. For a normal production visit (mode.isDesignLibrary = false) it renders the three placeholder slots. AppPlaceholder walks the route's rendering tree and resolves each Sitecore rendering name against componentMap.
const { layout, mode } = page const { route } = layout.sitecore // mode.isDesignLibrary = false → normal page render <header> <AppPlaceholder name="headless-header" page={page} componentMap={componentMap} rendering={route} /> </header> <main> <AppPlaceholder name="headless-main" page={page} componentMap={componentMap} rendering={route} /> </main> <footer> <AppPlaceholder name="headless-footer" page={page} componentMap={componentMap} rendering={route} /> </footer>
headless-header
Renderings authored in Sitecore for the header region
headless-main
Page body renderings (hero, content, etc.)
headless-footer
Footer renderings (Footer component from componentMap)
componentMap resolution:
AppPlaceholder reads each rendering's componentName from the layout JSON and looks it up in componentMap. Server components use component-map.ts; client components use component-map.client.ts.
// .sitecore/component-map.ts (registered components) new Map([ ['BYOCWrapper', BYOCServerWrapper], ['FEaaSWrapper', FEaaSServerWrapper], ['Form', { ...Form, componentType: 'client' }], ['PartialDesignDynamicPlaceholder', { ...PartialDesignDynamicPlaceholder }], ['Footer', { ...Footer }], ]) // Any rendering name not found → MissingComponent (silent in prod)
Server Components (default) Client Components (marked 'use client')
Legend
Server Component / server-side execution
Client Component / browser hydration
